# Door to Door

Mobile-first PWA for recording door-to-door visits and following them up later.

Members knock on units and record what they learn; the team returns months later and sees
the full history for that unit. Everything else exists to make capture reliable in the
field and keep the historical record clean.

Work is tracked as GitHub issues grouped into phase milestones. See the
[issue list](https://github.com/alphonsekoh/door-to-door/issues).

## Stack

| Layer        | Choice                                                                |
| ------------ | --------------------------------------------------------------------- |
| Framework    | Next.js 16 (App Router), React 19, TypeScript                         |
| Styling      | Tailwind CSS v4 (CSS-first config, no `tailwind.config.js`)           |
| Database     | PostgreSQL + Drizzle ORM, `drizzle-kit` migrations                    |
| Auth         | Auth.js v5 — Google SSO + credentials                                 |
| API contract | OpenAPI 3.1, types and Zod schemas generated by `@hey-api/openapi-ts` |
| Tests        | Vitest + Testing Library; Playwright for E2E smoke                    |
| PWA          | Serwist (`@serwist/next`)                                             |

## Core domain model

The household/visit split is the heart of the app and the thing most likely to be got wrong:

- A **household** is uniquely `(block, unit_number)`. Identity fields — name, contact,
  religion — live here as _latest known_, and are only ever updated with non-null values.
  A later visit that learns nothing must not erase what an earlier visit recorded.
- A **visit** is one knock, belonging to a household, a session and a member.
  `interest_level` and `description` live here and are **never overwritten**, so the
  interest trajectory over time stays visible.
- A **follow-up** attaches to the _household_, not the session, so it survives across outings.
- **One session is active app-wide at a time**, enforced by a partial unique index.
  Admins attach blocks to a live session; members self-select a block. Blocks are shared,
  never locked.
- `visits.id` is a **client-generated UUIDv7** — this is what makes the offline queue
  idempotent. Do not replace it with a database default.

## Rules

Each rule is marked **[CI]** if a check enforces it, or **[convention]** if it relies on
review. Do not weaken a CI rule to make a change pass; fix the change.

### Comments

**[convention]** Comment only where the _why_ is non-obvious. Keep them short. Never
restate what the code already says. A comment explaining a non-obvious constraint,
workaround or trade-off earns its place; `// increment the counter` does not.

### Tests

**[CI]** Every feature and every API endpoint ships with Vitest tests. Coverage thresholds
are enforced per-glob: **100%** for `src/server/**`, `src/lib/**`, `src/app/api/**`,
`src/db/**`, root-level `src/*.ts`; **90%** for `src/components/**` and `src/app/**`.

**[CI]** Three end-to-end flows run in a real browser at a phone viewport:
signing in, recording a visit, and an outing's whole lifecycle. They exist for what
jsdom cannot see - layout, stacking, and client-side navigation - after a sheet's save
button shipped underneath the bottom nav through three PRs and 1100 passing tests.
Keep the suite thin; Vitest owns coverage.

**[convention]** Write tests that assert behaviour. If a line can only be covered by a test
that asserts nothing meaningful, prefer deleting the unreachable code over writing a hollow
test. Coverage is the proxy; working software is the goal.

### API contract

**[CI]** `openapi.yaml` is the source of truth. Change the spec first, run
`npm run generate:api`, then implement. CI fails if generated output is stale.

**[CI]** Never hand-edit anything in `src/generated/**`. CI regenerates and fails if the
result differs, so a hand edit and a stale spec change are both caught. It is excluded from
lint and formatting precisely so an edit there stands out.

**[convention]** Only types and Zod validators are generated — the `@hey-api/sdk` and
client plugins are off because their HTTP runtime does not satisfy
`exactOptionalPropertyTypes`. Call the API with `fetch`, typed by `types.gen.ts` and
validated by `zod.gen.ts`.

**[CI]** Every route handler is wrapped in `withContract()`, which validates the request
_and the response_ against the generated Zod schemas. A response that drifts from the spec
must fail a test, not ship.

### Database

**[convention]** Schema changes are always generated with `drizzle-kit generate`, never
hand-written SQL. Never edit an applied migration; add a new one.

### Authorization

**[convention]** Re-check authorization server-side in every handler. Client-side role
checks are for UI affordance only and are never trusted. Hiding an admin button must never
be the only thing preventing an admin action.

### Generated route types

**[CI]** `PageProps` and `LayoutProps` come from `.next/types`, which does not
exist on a clean checkout. Both `lint` and `typecheck` run `next typegen` first for
that reason — anything type-aware that touches a route file needs it.

### TypeScript

**[CI]** No `any`. `noUncheckedIndexedAccess` is on, so array and record access yields
`T | undefined` — handle it rather than asserting past it. Prefer `type` over `interface`
(generated code uses type aliases, and interfaces permit declaration merging that can
silently widen a contract type).

### Commits

**[convention]** Conventional commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`).
Reference the issue with `Refs #N`; use `Closes #N` in the PR body, not the commit.

**[convention]** Branches are stacked: each feature branch bases off the previous one and
its PR targets that branch, not `main`. Merge top-down, and squash or rebase — a merge
commit on `main` gives every branch below it phantom conflicts.

## Workflow

**[convention]** Each issue moves through five subagents in `.claude/agents/`. The owner
(a human) makes product decisions and merges; no agent merges.

| Agent      | Does                                                              | Skip when                     |
| ---------- | ----------------------------------------------------------------- | ----------------------------- |
| `planner`  | Issue → slice plan; edits `openapi.yaml` only                     | No API, schema or sync change |
| `builder`  | Generate, server, UI, tests, gates; opens the stacked PR          | Never                         |
| `verifier` | E2E, phone-width device pass, proves new tests fail when broken   | Docs, config or server-only   |
| `reviewer` | Read-only review of invariants, authorization and conventions     | Never                         |
| `docs`     | Records decisions in `docs/tasks/`, flags conflicts, updates docs | Never                         |

Bugs found by the verifier or reviewer go back to the builder on the same branch. The
planner's open questions, and any decision conflict the docs agent flags, go to the owner
before work continues.

**[convention]** Decisions live in [`docs/tasks/`](docs/tasks/README.md), one file per
issue with stable `D-<issue>-<n>` IDs. Check them before deciding anything; supersede
explicitly, never silently. Architecture is in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md),
outside research in [`docs/RESEARCH.md`](docs/RESEARCH.md).

## Layout

```
src/
  app/          routes; app/api/** holds route handlers
  components/   React components
  lib/          framework-free helpers - prefer putting logic here, it is the
                easiest place to test and carries a 100% coverage threshold
  server/       server-only services and data access
  db/           Drizzle schema and client
  generated/    generated from openapi.yaml - never edit by hand
drizzle/        generated migrations - never edit by hand
```
